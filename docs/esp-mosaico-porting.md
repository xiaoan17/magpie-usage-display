# 从参考项目到 ESP32-S31 真机：移植过程与踩坑

本记录对应 2026-10-20 的一次真实适配。最终用户确认：屏幕、文字与颜色正常。
基础产品和大量代码来自 [peterroe/magpie-usage-display](https://github.com/peterroe/magpie-usage-display)，
其更早来源为 [jayyao97/codex-usage-display](https://github.com/jayyao97/codex-usage-display)。
完整贡献及许可证边界见 [ATTRIBUTION.md](../ATTRIBUTION.md)。

**下面主要是本地移植引入或暴露的问题，不是对上游原硬件版本的缺陷指控。**

## 从要解决的问题出发

目标是让已有 ESP-Mosaico 设备显示本机 Magpie 用量。上游已经有界面、统计、协议和 macOS Companion，
应复用这些工作；差异集中在 ESP32-S31 的 SDK、蓝牙栈、屏幕/触摸引脚以及 USB 启动方式。
因此保留四页 UI 和 BLE v4，把 Arduino 硬件层移植到 ESP-IDF，并用 NimBLE 接同一套协议。

验证拆成六层：USB 枚举 → 应用启动 → 加密蓝牙 → 实际收包 → 屏幕显示 → 真机颜色与触摸。
每层需要独立证据。编译通过、写入哈希正确、蓝牙连接成功，都不足以单独证明整机可用。

## 1. 固件已经写入，板子却停在下载模式

**症状**：能看到 USB 串口，应用管理接口没有响应，串口也无应用输出。

**证据**：不发送复位就能与 ROM bootloader 握手；读取应用头，与本地 Magpie 镜像一致。
所以既不是“没插线”，也不是“还没有写入”，而是程序尚未开始运行。

**处理**：不重新刷整机，先做正常启动复位。随后发现 `Magpie Display` 蓝牙广播和正常应用的新串口。
USB-OTG 从 ROM 到应用会换串口名称，必须按同一硬件身份重新查找端点。

**经验**：USB 存在只证明连接链路。不要把 ROM 枚举误认为应用健康，更不能因此反复全片擦除。

## 2. 蓝牙写入成功，应用却把所有数据当成空包

**症状**：电脑端可以发送，设备统计不更新。

**原因**：本地 NimBLE 移植把 `ble_hs_mbuf_to_flat()` 的返回值当作复制长度。
该函数返回 `0` 表示成功，真正的长度需要从最后一个输出参数获得。
因此成功收到的数据被以长度 0 交给解析器。

```c
uint16_t copied = 0;
if (ble_hs_mbuf_to_flat(ctxt->om, buffer, sizeof(buffer), &copied) != 0) {
    return BLE_ATT_ERR_UNLIKELY;
}
handle_status_write(buffer, copied);
```

**验证**：设备日志出现递增的 `status seq=...` 和模型名，电脑端同时记录 `Status delivered`。
状态包与操作结果包两条路径都修复，不能只修其中一处。

## 3. 蓝牙安全能力互相矛盾，首次配对不断断开

**症状**：macOS 返回 `Authentication is insufficient`，设备记录认证失败，反复连接又断开。

**原因**：本地设置了 SC-only，却配置 `NO_IO` 和 `sm_mitm=0`。当前 NimBLE 的
`ble_sm_verify_auth_requirements()` 在 SC-only 模式下也要求 MITM。
另一方面，Companion 一遇到通知订阅认证未完成就断开，没有给用户输入配对码的时间。

**处理**：屏幕可显示数字，所以使用 Display Only + MITM + Secure Connections，保留加密和绑定；
Mac 输入屏幕上的六位码。Companion 只对明确的认证/加密未就绪错误等待重试，最长 90 秒，
其他异常及断连继续立即失败，不无限重试。

**验证**：用户完成首次配对；设备记录 `encryption change status=0`。
随后更换电脑端进程、多次更新应用，仍能利用保留的绑定自动连接，不需要重复配对。

## 4. 能同步数据但黑屏：LCD 时钟和复位引脚反了

**症状**：设备端真实收包正常，屏幕仍然黑。

**原因**：最初的板型映射把 SCLK/RST 对调。官方 BSP 对 CoreBoard v1.2 使用
SCLK=42、RST=44，v1.0 则相反；不能把相似开发板或较早注释当成接线依据。

**处理**：按官方 BSP 引脚表与板型判断修正映射，使用该面板的 480×480 初始化序列。
通用 CO5300 默认序列对应另一种显示窗口，不能仅凭控制器名字相同就照搬。

**验证**：启动日志显示正确的 SCLK/RST；真正的画面验收最终由用户观察确认。
单向 SPI “命令发送成功”并不证明屏幕物理上显示正确。

## 5. 触摸初始化失败被忽略，继续运行掩盖了问题

**症状**：修复屏幕后启动日志出现 `invalid scl frequency` 和 `touch IO failed`。
早期移植代码在 `board_init()` 失败后仍继续运行，形成“蓝牙正常，触摸/显示不正常”的混合状态。

**原因**：旧触摸配置没有设置 I²C SCL 频率，并且用了另一款芯片的驱动。

**处理**：改用官方 CST9220 0.1.1 组件，400 kHz I²C，有限事务超时；初始化失败明确停止。
触摸读取失败不再使用旧数据，并在有效触摸时恢复亮屏。

**真机证据**：驱动读出 `chip=0x9220`、`project=0x6854`、`resolution=480x480`，
随后输出 `CST9220 touch ready`、`app: ready`。用户确认点亮并显示。

## 6. 已有画面，但颜色不对，文字重影或断裂

**症状**：用户确认画面出现，但颜色偏差、文字/图形像素错位或重影断裂。

**原因与处理**：

- 原 Arduino 显示库的 RGB565 绘制入口负责字节序转换；直接移植到 ESP-IDF SPI 发送后，
  这层转换丢失。现在仅在传输边界交换 RGB565 高低字节，保留 LVGL 和图片素材的原生格式。
- 最初调用异步绘制后立即 `lv_disp_flush_ready()`，可能让 LVGL 在 DMA 仍读取时重用缓冲区。
  现在等最后一个传输完成回调，再恢复字节序、归还缓冲区。
- 刷新区域按官方 BSP 的 4 像素横向对齐约束处理。

**验证**：原生 C 测试覆盖 RGB 三原色、白黑、越界哨兵、零长度与缓冲区还原。
使用同一套 UI 源码在电脑上生成四页图，确认字体与布局本身正常，再验证真实屏幕。
最后用户明确反馈“正常了！很好！”。

几项显示修复是分批/组合上线的，没有做逐项关闭的硬件消融实验；
因此能确认最终组合解决了问题，不能把每种视觉症状精确归因到唯一一个改动。

## 7. SDK 能编译也需要记录补丁，否则别人无法复现

实际 ESP-IDF 提交为 `e4df0c12f70daf0a7958e586e223c519fa9a1576`。
该提交声明版本 6.2.0，但版本描述可能仍显示 6.1-dev；不能只记录一个版本号。
PSRAM/XIP 相关链接脚本还使用了一行本地补丁：用 `MAX(ABSOLUTE(.), target)`
避免位置计数器向后移动。补丁已归档在 `ports/esp-mosaico/patches/`。

公开前在独立 fork 的空构建目录中重新解析依赖并完整编译成功。
这证明该源码配合记录的 SDK/补丁可构建，不等同于所有新 SDK 版本都兼容。

## 8. 最后才做长期使用配置

首次配对和实际收包成功后，才把 Companion 放到固定目录，安装当前用户的 LaunchAgent。
应用退出终端后继续运行，每 15 秒同步；日志保留成功发送与连接异常。
用从手动进程切换到后台进程的方式验证重连，不用“安装脚本返回成功”代替运行验收。

## 仍未覆盖的范围

- 只有一块 v1.2 / ESP32-S31 rev v0.0 真机；不是多个板型的兼容性认证。
- 没有完整测试 Mac 重启/重新登录、长时间离线、跨多台电脑或长时间压力运行。
- 原 Waveshare ESP32-S3 路径保留，但本次没有在原硬件上重新验收。
- 原始 Flash、NVS、配对码和个人用量日志不放进公开仓库。
